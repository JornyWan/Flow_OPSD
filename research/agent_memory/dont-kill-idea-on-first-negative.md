用户 2026-09-28 明确:**一个 idea 刚开始不 work,不要过早判负。** 应该通过 debug / 思考
找出**为什么**不 work,然后不断做**干净合理的**调整,直到找到真能 work 的形式。
最终形态可以和最初 propose 的不一样 —— 只要 (a) 干净、(b) 真的带来正面收益、(c) 理论上合理。

**Why:** 这个项目里绝大多数首轮负结果都伴随可定位的实现缺陷。已发生的实例:
规则版 repair 首轮 4 vs 12 判负,拆开后发现两个真缺陷(`missing` 类用全局 prompt 做条件、
自写的 `relative_position` 比判定器宽松导致 7/78 漏诊)—— 那不是方向不行,是实现不对。

**How to apply:**
- 首轮为负时,**先做失败模式分解**(按诊断类型/分层拆开成功率),定位是哪一类样本在拖。
- 区分三种负:**实现缺陷**(可修)、**口径缺陷**(对照/记账不对,如 §4.583 的探索成本未计)、
  **机制为负**(修完仍负)。只有第三种才是判负。
- 每轮调整必须是**机制性的**(针对定位到的原因),不是调参碰运气;并且改完要重新预登记判据。
- 但也不要无限迭代:预登记时就写清"第几轮仍负则关线"的条件(如 §4.586 的 V4 格)。

与既有规矩的关系:这条不推翻 [[dont-kill-ideas-before-running]](判负必须由真跑的 A/B 做),
而是加一层 —— **真跑出来的负也要先归因,再决定是不是方向的负。**
另见 [[opd-need-positive-results]]:不能只堆负结果。
